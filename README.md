# ScopeReady — прототип ядра

Аналитическое ядро, которое читает корпус проектных документов (тикеты, вики,
переписку) и говорит, чего в требованиях не хватает — по таксономии, а не «на
общих основаниях». Это прототип для проверки механики, а не продукт: ни веб-слоя,
ни живых коннекторов, ни калибровки весов здесь нет.

---

## 1. Зачем он и что именно проверяет

Ключевое решение, вокруг которого построено всё остальное: **это аудит по чек-листу, а не вопрос к базе знаний.** Решение не строится вокруг того чтобы просто спросить модель «чего не хватает в этих требованиях». Такой вопрос даёт правдоподобный, неизмеримый и невоспроизводимый ответ.

Вместо этого — N независимых проверок покрытия, по одной на категорию
таксономии. Каждая обязана либо привести цитату из корпуса, подтверждающую
покрытие, либо объявить отсутствие. Отсюда три следствия, ради которых всё и
затевалось:

- метрики становятся покатегорийными: «recall по `acceptance_criteria` вырос
с 0.6 до 0.8, precision не упал» — это утверждение, которое можно проверить;
- библиотека промптов становится **данными, а не кодом**: одна категория —
одна проба — одна метрика;
- утверждение об отсутствии становится **опровержимым** одним контрпримером,
и следующий шаг конвейера именно этим и занят.

**Что считается успехом прогона.** Не «отчёт выглядит умно», а: профиль совпал
с ожидаемым; неприменимые категории отсеяны с названной причиной; каждая цитата
дословно нашлась в корпусе; категория, закрытая только в вики, попала в
suppressed, а не в пробелы; повторный прогон дал байт-в-байт тот же JSON.

## 2. Как он устроен



### Конвейер

```
ingest ──► чанкинг ──► индекс (FTS5 + векторы)
                              │
                              ▼
        профиль проекта ──► гейт применимости ──► пробы (fan-out)
                                                       │
                                        верификация цитат, где покрытие
                                                       │
                                            ▼──── кандидаты в пробелы
                                        поиск опровержения по всему корпусу
                                                       │
                                     скоринг ──► черновики вопросов ──► отчёт
```

Модель вызывается ровно в четырёх местах: профиль, проба по категории, узкий
вопрос опровержения, черновики вопросов. Скоринг и определение места покрытия —
детерминированный код, не модель.

### Модули


| Модуль                             | За что отвечает                                                                                                   |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `models.py`                        | Pydantic-модели корпуса и результата. Инварианты живут здесь                                                      |
| `text.py`                          | Нормализация под индекс, санитизация FTS-запроса, сверка цитат                                                    |
| `chunking.py`                      | Структурный чанкер: путь заголовков, окно токенов, дробление без обрезки                                          |
| `ingest.py`                        | Markdown + YAML front matter → документы                                                                          |
| `store.py` / `corpus.py`           | Интерфейс хранилища и его реализация на SQLite. `sqlite3` импортирует только `corpus.py` — это проверяется тестом |
| `embeddings.py`                    | `bge-small`, `gte-modernbert` и хеш-стаб за одним интерфейсом                                                     |
| `retrieval.py`                     | Слияние лексического и векторного каналов через RRF                                                               |
| `taxonomy.py` / `applicability.py` | Загрузка рубрики и гейт применимости                                                                              |
| `llm.py`                           | Ollama, стаб и дисковый кэш за одним интерфейсом                                                                  |
| `prompts.py`                       | Сборка запроса: инвариантный префикс и переменный хвост                                                           |
| `verification.py`                  | Проверка цитат и определение места покрытия                                                                       |
| `analyze.py`                       | Конвейер и fan-out                                                                                                |
| `report.py`                        | Рендер Markdown и JSON                                                                                            |




### Три решения, которые видно в коде

**Таксономия — данные.** Движок не знает ни одной категории по имени. Категория —
запись в `taxonomy/gaps.client_agreement.yaml` с полями `probe`, `covered_when`,
`insufficient_when`, `retrieval_queries`, `weight`, `applies_when`. Целевая геймдев-вертикаль (движок, сертификация платформ, live-ops, возрастной рейтинг) добавлена **данными, а не кодом** — она включается признаком профиля `is_game_project`.

Выражение `applies_when` разбирается через `ast` с белым списком узлов. Никакого
`eval`, только `yaml.safe_load`: файл рубрики лежит рядом с кодом и иначе стал бы
способом выполнить код правкой конфига.

**Экономика вызова заложена в разметку запроса.** Запрос = системный промпт +
корпус единицы анализа (байт в байт одинаковые для всех проб) + короткий хвост.
Первая проба идёт одна и греет KV-кэш, остальные — с ограничением параллелизма:
параллельные слоты Ollama держат независимые кэши, и наивный `gather` заставил бы
каждый слот заново прожевать весь префикс.

**Цитата — лицензия на вердикт.** Вердикт `covered`, ни одна цитата которого не
нашлась в корпусе, движок понижает до `absent` с предупреждением. Уверенность при
этом не занижается: понижение утверждает «доказательства покрытия нет», а не «мы
менее уверены, что пробел есть».

### Что измерено, а не предположено

Две вещи проверены на машине (Apple M1 Pro, 32 ГБ, `qwen3-vl:8b`) и меняют
то, как стоит этим пользоваться:

1. **Описания из JSON-схемы до модели не доходят.** Запрос с описаниями и без них
  даёт одинаковое число promt-токенов. Поэтому формат ответа `prompts.py`
   выписывает в текст промпта, а не полагается на docstring'и схемы.
2. **Структурированный вывод — главная статья расходов прогона.** На одном и том
  же содержимом: без `format` — 87 с, 20.7 токена/с; с `format` — 150 с,
   **0.7 токена/с**. Разницу в 30 раз одним измерением не объяснить, но
   практический вывод твёрдый: на маленькой локальной модели полный прогон
   занимает десятки минут, и это ожидаемо, а не поломка.

## 3. Что настроить

Нужны три вещи: Python 3.13 с `uv`, локальная Ollama и один скачанный
эмбеддер (тянется автоматически при первом запуске, ~130 МБ).

### macOS

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
brew install ollama && brew services start ollama
```



### Windows (PowerShell)

```powershell
irm https://astral.sh/uv/install.ps1 | iex
winget install Ollama.Ollama
```



### Дальше одинаково

```bash
uv sync
```

`uv sync` ставит и `sentence-transformers` с torch — порядка 2.5 ГБ, потому что
эмбеддер по умолчанию настоящий (`BAAI/bge-small-en-v1.5`, ~130 МБ весов,
скачиваются при первом обращении). Если torch не нужен, весь конвейер целиком
проходится на хеш-стабе.

### Прогон без единого вызова модели

```bash
uv run scopeready index fixtures/corpus --db runs/corpus.db --embedder stub
```

```bash
uv run scopeready analyze --db runs/corpus.db --embedder stub --backend stub --format both
```

Это проходит весь конвейер меньше чем за секунду. Стаб отвечает детерминированно
и цитирует настоящие фрагменты корпуса, поэтому проверяются все ветки: покрыто
внутри единицы, покрыто снаружи, пробел, пробел закрытый опровержением. Так
удобно работать над рубрикой, отчётом и скорингом — там, где модель не нужна.

### Прогон с настоящей моделью

```bash
ollama pull gpt-oss:20b
```

```bash
uv run scopeready doctor --model gpt-oss:20b
```

```bash
uv run scopeready index fixtures/corpus --db runs/corpus.db
```

```bash
uv run scopeready analyze --db runs/corpus.db --backend ollama --model gpt-oss:20b --format both
```

`doctor` проверяет ровно то, что иначе падает поздно и непонятно: собран ли
SQLite с FTS5 (актуально на Windows), грузится ли эмбеддер, валидна ли рубрика,
поднята ли Ollama, скачана ли модель и компилируются ли схемы ответов в
грамматику. Схема, которую сервер не может превратить в грамматику, вернёт 400 —
и узнать это на старте лучше, чем на пятнадцатой минуте прогона.

Полезные команды помимо `analyze`:


| Команда                                                          | Зачем                                                                               |
| ---------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `taxonomy select --granularity epic --feature has_payments=true` | Таблица гейта: что спросят и почему, без корпуса и без модели                       |
| `search "who may delete a workspace" --channels`                 | Лексика, векторы и слияние в трёх колонках                                          |
| `probe acceptance_criteria --show-prompt`                        | Одна проба и точные байты запроса. Основной цикл работы над формулировками          |
| `analyze --dry-run`                                              | Собрать все промпты и не вызвать модель. Быстрый ответ на «не разнесло ли контекст» |




### О моделях

`--model` по умолчанию `gpt-oss:20b` (~13 ГБ) — целевая модель: MoE, уровни
reasoning-effort, штатная поддержка структурированного вывода. Альтернативы того
же класса за тем же адаптером — `qwen3:14b`, `qwen3:30b-a3b`.

Проверялось это на `qwen3-vl:8b`, потому что она подходит под ресурсы имеющегося ПК. Проводку она проходит: на пробе `roles_and_permissions` вернула `covered` с настоящей  
дословной цитатой из нужного тикета, а на шаге профиля — двенадцать признаков  
с обоснованиями (см. ниже). Но это vision-модель, и на шаге суждения  
от неё ждать нечего. **Пока не скачана модель класса** `gpt-oss:20b`**, числа**  
**качества читать нельзя** — ожидаемы выдуманные идентификаторы фрагментов,  
коллапс вердиктов (все категории приходят `absent` с уверенностью 0.9) и  
уверенное «covered» с перефразированной цитатой. Первое и третье движок ловит и  
пишет в предупреждения; читать их — часть работы.

Про время — измеренное, а не прикинутое. Под грамматикой структурированного
вывода `qwen3-vl:8b` выдаёт около 0.7 токена в секунду. Один вызов профиля на
фикстуре: 11081 prompt-токен, 948 токенов ответа, **около 19 минут**. Полный
прогон — это восемнадцать вызовов, то есть часы, а не десятки минут. Дисковый
кэш делает повтор бесплатным, поэтому итерации по отчёту, скорингу и рубрике не
стоят ничего; платится только первый прогон. На `gpt-oss:20b` со штатной
поддержкой структурированного вывода ожидания другие, но здесь они не измерены.

Что при этом ответила модель — стоит посмотреть, потому что ответ хороший.
Двенадцать признаков, все с обоснованием и ссылкой на конкретный фрагмент:
`has_existing_codebase` — по legacy-таблице `shared_links` из SCOPE-5,
`has_external_integrations` — по «invitations are sent through the existing
transactional email service» из SCOPE-3. Игровые и мультиязычные признаки —
false, как и должно быть.

Один ответ спорный и показателен: `has_payments: true`. В эпике есть фраза, что
Team-план «already exists and is billed through the current subscription flow;
nothing about billing changes in this epic». Формально проект деньги трогает —
и гейт после такого профиля спросит про PCI, хотя этот эпик про платежи не про
них. Профиль поэтому и стоит в отчёте **первым**: ошибка здесь молча меняет
список вопросов дальше, и единственная защита от неё — что её видно.

## 4. Как обогащать своими данными

Корпус — папка Markdown-файлов с YAML front matter. Это единственный адаптер, и
он же контракт: всё, что живой коннектор к Jira должен был бы заполнить, здесь
видно как именованное поле.

```markdown
---
source_kind: tracker          # tracker | wiki | chat | file
source_name: jira             # ^[a-z0-9][a-z0-9_-]*$ — часть идентификатора документа
source_id: SCOPE-42
title: "Audit log export"
corpus_role: requirement      # requirement | context — обязательно, не выводится
url: https://example.invalid/browse/SCOPE-42
author: Dana Reyes
author_side: customer         # customer | executor | unknown
created_at: 2026-03-09T13:25:00+00:00
item_label: Story
status: To Do
parent_source_id: SCOPE-1
---

Тело документа в Markdown. Заголовки задают путь секции и в цитируемое тело
не попадают.
```

Обязательны только `source_kind`, `source_name`, `source_id`, `title` и
`corpus_role`. Остальное необязательно, но `created_at` и `author_side` стоит
заполнять: на них держатся свежесть в переписке и правило «заказчику цитируется
только то, что написал он сам».

`corpus_role` **задаётся явно и никогда не выводится.** `requirement` — заявленный
объём, то, что может попасть под аудит. `context` — всё остальное, что может
закрыть пробел: вики, переписка, регламенты. Разница определяет, попадёт ли
находка в «пробелы» или в «требование есть, но не здесь», а угаданная роль — это
вердикт, который потом не объяснить.

### Полный цикл

```bash
uv run scopeready index data/local/mycorpus --db data/local/mycorpus.db
uv run scopeready analyze --db data/local/mycorpus.db --unit jira:PROJ-1 --granularity epic --backend ollama --format both
```

`data/local/` — в `.gitignore`. Реальные экспорты заказчика туда и только туда:
это ограничение по IP и NDA, а не гигиена. Отчёты пишутся в `runs/`, тоже вне
гита.

### Что важно знать при своих данных

- **Единица анализа** — корневой документ плюс его прямые дети (`parent_source_id`).
Всё вне её всё равно ищется — на этом и держится опровержение, — но покрытие,
найденное снаружи, попадает в отдельную секцию отчёта.
- **Смена эмбеддера требует переиндексации.** Одно пространство эмбеддингов на
файл; при попытке спросить базу другой моделью прототип откажется работать и
скажет, чем она была построена. Молчаливый откат на лексический поиск был бы
хуже: «поиск сломан» выглядело бы как «поиск стал хуже».
- **Гранулярность** — свойство прогона, а не источника. `--granularity epic`
спросит категории уровня эпика; `project` спросит про гарантию, хостинг и
change request, которые на уровне эпика не имеют смысла.
- **Веса —** `seed`**.** Они выведены из общих соображений о том, где fix-price
проекты теряют деньги, и не измерены. Осмысленно сравнивать их порядок, а не
абсолютные значения. Перевести их в `calibrated` может только сбор статистики
по закрытым проектам — в прототип это не входит.
- **Корпус англоязычный.** На этом держатся стеммер FTS5 и качество эмбеддера
при таком размере. Русский корпус потребует заменить две вещи — эмбеддер и
токенизатор индекса; шов для этого — `text.normalize_for_index` и интерфейс
`Embedder`.
